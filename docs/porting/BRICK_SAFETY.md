# α1 刷机防砖分析（基于固件实证）

> 结论先行：**索尼在这台相机里内置了相当完整的防砖机制，加上我们的实验设计，可以把风险压到"接近官方固件升级"的水平；但有一种风险无法消除——我们做不了整机 NAND 备份（senser 深通道被锁），所以不存在 100% 的安全网。是否刷机，最终决定权在你。**

---

## 一、索尼内置的防护（全部在固件里找到实证）

### 1. NOR bootloader 独立于主系统，且我们有 Force Update 恢复通道
- NOR 启动加载器（`loader_nor.bin`）在**独立的 NOR flash 芯片**里，不在 NAND 主存储上
- 它含有 `BOM:[Chaplin] Selected Force Update mode` 和 `LDR:XFORCE_UPDATE` 字符串——**相机有"强制更新模式"**
- 启动时它会读按键（`LDR:<< KEY E / L / D >>`）决定进入哪种模式
- **含义**：就算主 Linux 系统被刷坏、无法启动，NOR loader 照样先跑，能进强制更新模式重新刷机。**这是索尼官方设计的恢复通道，就是用来救刷坏的机器的。**
- **我们的所有改动都不碰 NOR loader**（只动 nflasha15 的 /usr 区和协处理器数据），这条命根子始终在。

### 2. 更新流程"先校验、后写入"，且逐组件 CRC32
- `config.xml`（更新流程定义）里每个组件都是 `us_crc32sum.sh`（CRC 校验）**在前**，firmup/写入脚本**在后**
- 第一个 proc（config_sum）一开始就是 CRC 校验 + chkfirm.sh（主/副 LSI 检查），**任何写入之前先做完整校验**
- 包级检查（如果查 256B 签名）逻辑上也在第一个 proc 之前 → **校验失败的包会在写入任何数据之前被拒**，旧固件原封不动

### 3. 刷机前自动保护用户数据
- `startupdate.sh` 第一件事就是 `KEEP_BACKUP -p /ramdsk`：**先把相机的 Backup.bin（你的设置、校准数据）保存起来**
- 然后保存 model/region（dat2/dat3）
- 刷完再恢复——和官方升级完全一样（我们的重打包不动 updater，这些流程原样保留）

### 4. 启动链签名与我们的改动不冲突
- NOR loader 流程：`Init InfSec → Sign 检查 → Jump Kernel`
- 被签的是**启动链**（loader + 内核），我们**不修改** nflasha3 的内核和 NOR loader → 启动链签名保持索尼原厂有效
- 我们改的是 nflasha15（/usr 应用层）和协处理器数据，这些在启动链签名之外

## 二、我们的实验设计（把风险压到最低）

### 测试阶梯——每一步过了才走下一步，绝不跳步

| 步骤 | 内容 | 风险 | 失败后果 |
|---|---|---|---|
| **第 0 步** | **字节一致重打包**（内容和官方 .DAT 一模一样） | **≈ 0** | 相机拿到的字节和官方升级完全相同，无法区分 |
| **第 1 步** | 改一个无关紧要的文本字节（如版本字符串） | 极低 | 若验签→写入前被拒，旧固件不动；若通过→只是改了个文本 |
| **第 2 步** | 混合 AI 组件（cpapp-b.bin + 字典 + AI 框架） | 中 | 若内容不兼容→主系统可能起不来，但 **Force Update 还能刷回官方** |

### 关键原则
- **第 0 步必须先做**：它验证"我们的重打包在真机上被接受"，而且是字节级等同官方文件，**这一步本身不会比官方升级更危险**
- **永不触碰**：NOR loader、nflasha1 updater 分区、nflasha3 内核——索尼签名的启动链完整保留
- **手上随时备好**：官方原版 .DAT（两份都有）+ 确认 Force Update 按键组合——万一出问题，强制更新刷回官方即可

## 三、诚实说明：这些风险防不了

1. **做不了整机 NAND 备份**。senser 深通道（pull/bootrom）在国行机上被锁（此前实测 Error 128），所以**没有"完整镜像可以回刷"这一终极保险**。万一 Force Update 也因某种我们没发现的校验而拒绝，且主系统已坏，就真的砖了。
   - 缓解：Force Update 刷的对象是**索尼官方固件**（字节和官网下载的一样），它自己的恢复通道没理由拒自己的包——这正是该通道的设计目的。
2. **256B 尾签的验证时机无法离线确定**。逻辑上它在写入前检查（否则校验毫无意义），但万一索尼设计在写入后校验，存在"写到一半失败"的窗口。
   - 缓解：第 1 步先只改一个文本字节试探，即使真出这个窗口，破坏也仅限于单个组件。
3. **协处理器固件（cpapp-b.bin）的硅版本兼容性**。dtb 显示两台同平台，但如果 α1 的协处理器硅片是旧修订版，α1 II 的协处理器固件可能起不来——表现为 AF/成像异常，但**不会砖**（主系统还在，能 Force Update 刷回）。
4. **刷机中途断电**。这和官方升级的风险一样，不因我们的改动而增加。

---

## 四、建议

- **如果你只想"看看能不能成"而不想冒任何险**：第 0 步（字节一致重打包）风险等于官方升级，可以先只做这一步——成了就证明管线通了，后面收手也值。
- **第 1 步（改一字节）是签名问题的判官**，风险极低，建议做。
- **第 2 步（AI 移植）是唯一有实质内容风险的一步**，做之前确认：Force Update 按键能进、官方 .DAT 在手、电量充足、电池+电源双保险。
- **任何一步相机出现异常**：别慌着反复开机，直接进 Force Update 刷官方包。

一句话：**索尼给的恢复通道（Force Update + 独立 NOR loader）+ 我们的"不碰启动链 + 阶梯测试"设计，把砖的概率压得很低；但因为没有 NAND 全量备份，我不能向你承诺零风险——最后的 go/no-go 由你定。**
